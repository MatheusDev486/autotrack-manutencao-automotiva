3. Possíveis Perguntas da Banca e Como Responder (Colo de Prova)

Abaixo estão as 8 perguntas mais prováveis que o professor de Banco de Dados fará durante a arguição, com as respostas técnicas exatas:

1. Por que vocês escolheram o MySQL e como garantiram que não houvesse persistência simulada?
"Optamos pelo MySQL 8.x por ser um SGBD amplamente adotado no mercado, com suporte a transações ACID e motor InnoDB. Garantimos a persistência real conectando o Back-end através do driver nativo mysql2/promise com um Pool de Conexões configurado no arquivo src/config/database.js. Todas as operações de CRUD executam comandos SQL puros (INSERT, SELECT, UPDATE, DELETE) direto nas tabelas do banco de dados autotrack_db, sem qualquer uso de SQLite, arquivos JSON locais ou memória temporária."
💡 Dica de ouro: Diga que se você reiniciar o servidor ou fechar o navegador, todos os dados continuam intactos no MySQL Workbench.
2. O que acontece se eu tentar excluir um cliente que já possui veículos vinculados?
"O MySQL impede a exclusão automaticamente através da restrição de chave estrangeira com a regra ON DELETE RESTRICT definida em database/schema.sql. Quando essa operação é tentada, o motor InnoDB gera o erro MySQL 1451 (ER_ROW_IS_REFERENCED_2). No Back-end, nós capturamos exatamente esse código de erro e enviamos uma resposta HTTP 409 Conflict amigável para o Front-end, informando ao usuário que ele não pode deletar um cliente sem antes desvincular seus veículos."
💡 Dica de ouro: Mostre a linha 24 do arquivo src/config/database.js onde o erro 1451 é tratado explicitamente!
3. O que é o modo ONLY_FULL_GROUP_BY do MySQL 8 e como a Query 2 de vocês atende a essa exigência?
"No MySQL 8, o modo padrão ONLY_FULL_GROUP_BY rejeita consultas em que uma coluna não-agregada é listada no SELECT sem estar presente na cláusula GROUP BY, evitando resultados indeterminados ou ambíguos. Na nossa Consulta 2 (Gastos por Veículo), nós colocamos explicitamente todas as colunas descritivas (v.id, v.placa, v.marca, v.modelo, v.ano, c.nome) no GROUP BY, reservando para funções de agregação apenas o COUNT(m.id), SUM(m.valor) e AVG(m.valor)."
4. Como vocês preveniram falhas de segurança do tipo SQL Injection?
"Não utilizamos concatenação de strings para montar comandos SQL dinâmicos. Em todos os controllers (clienteController, veiculoController, etc.), utilizamos Prepared Statements com marcadores de parâmetro posicionais (?). Dessa forma, o driver mysql2 envia a query pré-compilada separadamente dos dados de entrada do usuário, tratando qualquer caractere especial como dado literal e impedindo a injeção de instruções maliciosas."
5. Qual é a diferença entre a consulta com JOIN e a Subconsulta implementada?
"A consulta com JOIN (INNER JOIN) combina horizontalmente linhas de 3 tabelas diferentes em uma mesma projeção através da correspondência de chaves (m.veiculo_id = v.id e v.cliente_id = c.id). Já a Subconsulta é uma query aninhada dentro da cláusula HAVING: a subquery calcula dinamicamente a média global de gastos de todos os veículos da oficina (SELECT AVG(...)), e a query externa filtra apenas os grupos de veículos cujo somatório individual de gastos é estritamente superior a esse valor de corte."
6. Por que vocês usaram HAVING em vez de WHERE na consulta de subquery?
"Porque a cláusula WHERE atua como filtro de linhas individuais antes de qualquer agrupamento ou função agregada ser processada. Já a cláusula HAVING é avaliada após o cálculo das agregações (GROUP BY). Como o critério de comparação depende de uma soma acumulada (SUM(m.valor)), a sintaxe do SQL exige obrigatoriamente o uso de HAVING gasto_acumulado > (subquery)."
7. Como vocês modelaram os tipos de dados e restrições no schema?
"Utilizamos tipos padronizados: valores monetários usam DECIMAL(10,2) para evitar erros de arredondamento de ponto flutuante; quilometragem e ano usam INT; datas usam DATE e DATETIME com DEFAULT CURRENT_TIMESTAMP; e categorias fixas (como o tipo da manutenção 'PREVENTIVA'/'CORRETIVA' e o status da OS) usam ENUM. Adicionalmente, aplicamos constraints UNIQUE na placa do veículo, no CPF e no e-mail dos clientes."
8. Se o sistema crescer para 500 mil manutenções, como garantiriam a performance do banco?
"Para manter alta performance em escala: 1) Garantiríamos índices B-Tree nas chaves estrangeiras (veiculo_id e cliente_id) e na coluna de busca temporal (data_manutencao); 2) Implementaríamos paginação com LIMIT e OFFSET na API para não sobrecarregar a memória com transferências em massa; e 3) Analisaríamos o plano de execução das consultas através do comando EXPLAIN do MySQL."
